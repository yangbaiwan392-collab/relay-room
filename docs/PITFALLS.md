# PITFALLS — 这份项目踩过的坑（按遇到顺序）

> 每一条都真实发生过，写清"症状 / 原因 / 修法"，省得下一个人重踩。
> 标 ⚠️ 的是会直接让整轮跑废的坑。

## 一、模型与提示

### 1. ⚠️ 思考型模型返回空回复

- 症状：发言是空字符串，或 `(empty reply)`；日志里 tokens 正常。
- 原因：Qwen3 / Qwen3.5 / minicpm 这类模型把 `num_predict` 全花在 `thinking` 上，正文没开始。
- 修法：请求体里显式 `"think": false`；空 content 时回退到 `thinking` 字段；再加一次"必须给正文"的重试。
  本项目 `speaker.py` 三者都做了。

### 2. ⚠️ 提示措辞必须和校验逻辑一致

- 症状：87% 的首版发言被退回重写，最终接续率反而掉到 11%。
- 原因：为了"防回声"把提示改成了"不要复述原话"，但校验仍是"必须引用 ≥6 字原话"——模型照提示做，
  校验照旧不过。
- 修法：`relay_check` 与提示同源：`quote` 模式要求短引用，`respond` 模式才允许"回应观点"。
  改任何一侧，另一侧必须跟着改。

### 3. 全禁类比会让内容变干

- 症状：类比率从 47% 降到 3%，但回复从 80–100 字缩到 30–50 字，变成提纲。
- 修法：用"配额"（每 N 轮最多 1 次）而不是"全禁"；或者只对最上瘾的 speaker 禁。

### 4. "给模型几个开场变体，让它自己换"——它做不到

- 症状：给了 3 个变体，它挑一个当新口头禅，10 轮里用 6 次。
- 修法：变化交给主管：每轮随机指定一个变体，且不连续重复；只在钱 12 轮发牌，之后停。

### 5. 结构化摘要会杀死接力

- 症状：把上一位的话压成"主张/理由/落点"后，接续率从 38% 掉到 8%。
- 原因：模型需要**可引用的原话**，不是要点；摘要一压，锚点就没了。
- 修法：接力传原话（末 100 字），不要摘要。

## 二、机制

### 6. ⚠️ 平行模式（panel）几乎没有接续

- 症状：4 个模型各自回答"话题+角度"，引用上一位的比例只有 2%，15 轮后开始复读。
- 修法：改成 relay 串行接力（主管把上一位的话递给下一位）；这是本项目最核心的改动。

### 7. ⚠️ 重写必须"替换"，不能"追加"

- 症状：同一轮同一人出现 2–3 条（原始版 + 修订版），观感像复读；统计也重复计数。
- 修法：修订写入 `seq>=1` 后，把旧版本标 `superseded`；所有视图（对话窗口、query、speaker 上下文）
  只取每个 `(round, sender)` 的最新版本。

### 8. ⚠️ `has(seq=0)` 和 superseded 过滤会互相打架

- 症状：日志显示"0/4 spoke"，或者第二轮修订永远等不到（每轮卡 90 秒超时）。
- 原因 1：发言计数用了被 superseded 过滤后的 `seq=0` 查询 → 明明说了却被算成 0。
- 原因 2：判断"这是不是修订"时写了"seq=1 还没写过"；第二遍修订（seq=2）就永远不被认。
- 修法：修订判定改成"`run.revise` 指向我，且目标 seq 还没写"；计数用 `latest_utterances()`
  （每个 speaker 每轮取 MAX(seq)）。

### 9. ⚠️ 严格引用对 4B/7B 是硬成本

- 症状：约 80% 首版不合格，改写量 0.8 条/发言，耗时翻倍。
- 修法（按效果排序）：
  1. 换更大的模型（7B 只 +3pp 接续，不要期待它把改写率砍半）；
  2. 接受"后台重写、前台只看最终版"（替换式重写）；
  3. 改 `relay_check: respond`（改写降到 64%，但接续掉到 11%——不推荐）。

### 10. 守卫会互相触发

- 症状：禁句重写后触发去重，去重后触发 relay 校验，一轮改 3 次。
- 修法：每类守卫每轮最多 1 次；顺序固定（relay → phrase → dedup）；`repair_timeout` 设 45 秒左右，
  超时直接放过，不要无限等。

## 三、工程 / Windows

### 11. ⚠️ urllib 会走系统代理，代理挂了本地也连不上

- 症状：本地 Ollama 和云端同时 `WinError 10061 connection refused`；curl 却正常。
- 原因：Python `urllib` 默认读取系统代理设置；代理进程挂了，所有请求都被拽向死端口。
- 修法：所有 HTTP 调用统一用 `build_opener(ProxyHandler({}))` 绕过代理（本项目 speaker 和 conductor 都这么做了）。

### 12. 两个下载进程写同一个文件 → 文件损坏

- 症状：4.36 GB 的 GGUF 下成 6.11 GB，`ollama create` 失败。
- 原因：旧脚本报错后没退出，和新脚本并发写同一个 `.gguf`。
- 修法：下载器先检查同名文件/进程；单文件单进程；下完校验大小 + SHA256。

### 13. Ollama 环境变量对已运行进程不生效

- 症状：设了 `OLLAMA_MAX_LOADED_MODELS=4`，还是按 3 个加载，频繁换入换出。
- 修法：在**启动 Ollama 的同一进程**里设置环境变量，然后重启 Ollama；用户级 `setx` 不会改已运行进程。

### 14. 显存要按"权重 + KV"一起算

- 实测：5×3B ≈ 15.0 GB（92%）；3×7B ≈ 15.9 GB（97.5%）；2×7B + 2×4B ≈ 15.4 GB。
- 16 GB 卡上不要同时跑 4 个 7B；`num_ctx` 减半能省 KV，但会削弱接力上下文。

### 15. Windows PowerShell 5.1 的坑

- 不支持内联 `if` 表达式（`((if ...))` 直接语法错误）→ 拆成变量。
- 脚本里的中文标点会被当字符串定界符 → 逻辑写进 `.py`，PowerShell 只做启动。
- `.cmd` 必须 CRLF 行尾，否则 `if errorlevel` 多行块会崩。
- 别按命令行关键字杀进程（会误杀自己的作业运行器），按 PID / 端口杀。

### 16. 中文终端宽度

- 症状：`{name:<8}` 按字符数补齐，中文名只有 4 列，表格错位；长中文行不换行。
- 修法：按显示宽度计算（CJK 记 2 列），用 `unicodedata.east_asian_width` 实现换行/补齐（`chat-view.py`）。

### 17. 会话/日志目录要排除在版本控制外

- `runs/` 会很快到几百 MB（SQLite + 每轮日志 + VRAM 采样）。
- 本项目 `.gitignore` 已排除 `runs/`、`*.png`、`__pycache__/`。

## 四、网络 / 成本

### 18. 云端调度 JSON 会被截断

- 症状：主持人调用 `unparsable`。
- 原因：`max_tokens` 太小，或模型先输出解释再输出 JSON。
- 修法：`max_tokens=1500`；解析失败时按字段逐个正则兜底；再失败重试一次"只输出 JSON"。

### 19. 云端成本几乎可以忽略

- 实测：每 8 轮一次，200 轮约 24 次调用、3 万 tokens；单次 1–1.5k tokens。
- 真正贵的是本地时间（改写），不是云端。

### 20. ⚠️ 密钥绝不进仓库/命令行

- 只从环境变量读（`CONDUCTOR_API_KEY`）；不要写进 config、不要放进命令行参数（会进 shell 历史与进程列表）。
- 仓库里不含任何密钥；`models.json` 兜底也仅作为本机便利，不复制、不提交。
